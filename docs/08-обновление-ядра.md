# Обновление ядра Битрикса — пошаговый runbook

Текущее состояние: **1С-Битрикс 23.300.0**, PHP **8.3.8**, nginx + php-fpm (Apache остановлен), MySQL 5.7.
Дата подготовки: 11.11.2026.

## 0. Предусловия (чего сейчас не хватает)

1. **Логин и пароль аккаунта обновлений 1С-Битрикс** (раздел «Настройки → Обновление платформы»).
   Подписка на обновления истекла **03.03.2026** (`~support_finish_date`) — возможно, потребуется продление.
2. **Доступ в админку** (администратор сайта).
3. Окно работ / уведомление пользователей (обновление ядра может занять 10–40 минут).
4. Свободное место ≥ 5 ГБ (сейчас 11 ГБ — достаточно).

Проверка перед началом:
```bash
mysql -N -e "SELECT VALUE FROM sitemanager.b_option WHERE NAME='~update_autocheck_result';"
grep SM_VERSION /home/bitrix/www/bitrix/modules/main/classes/general/version.php
```

## 1. Бэкап (обязательно)

На сервере:
```bash
bash /root/backup-prod.sh
```
Создаёт в `/root/backups/`: дамп БД + архив кода.
Актуальные бэкапы (11.11.2026): `db-sitemanager-20261111-194412.sql.gz`, `site-code-20261111-194412.tgz`.

## 2. Обновление на STAGING (сначала там)

1. Зайти в админку staging (`stage.bobrovylog.ru/bitrix/admin/`) — временного админа при необходимости создать тем же способом, что использовался для тестов, и удалить после.
2. **Настройки → Обновление платформы** → ввести логин/пароль обновлений → «Проверить обновления».
3. Зафиксировать список доступных обновлений и версий модулей (доступно только то, что вышло до окончания подписки).
4. Установить обновления, дождаться завершения.
5. Проверить:
   - front-end: 44–119 внутренних ссылок, ключевые страницы — 200;
   - админка: 12–15 разделов — 200;
   - `php -l` основных изменённых файлов не требуется — обновление ядра идёт пакетами.
6. Сравнить паритет staging/prod (скрипт сравнения ссылок использовался в предыдущих раундах).

## 3. Обновление на ПРОДЕ

1. Повторить бэкап (`backup-prod.sh`) — свежая точка отката.
2. Админка прода → «Обновление платформы» → обновить ядро и модули.
3. Наблюдать `/var/log/nginx/default_error.log`, `/var/opt/remi/php83/log/php-fpm/error.log`.
4. Выполнить smoke-тест:
```bash
for u in / /raspisanie/ /services/ /news/ /about/ /tenders-ended/ /bitrix/admin/; do
  curl -sS -o /dev/null -w "%{http_code} $u\n" -H "Host: bobrovylog.ru" "http://127.0.0.1$u"; done
```
5. Проверить агенты: `mysql -N -e "SELECT MAX(LAST_EXEC) FROM sitemanager.b_agent;"` (обновляется ежесекундно-минутно).
6. Проверить формы (без реальной отправки почты — тестовая заявка только на staging).

## 4. Откат при проблемах

- **Код**: `tar xzf /root/backups/site-code-<stamp>.tgz -C /home/bitrix/www`
- **БД**: `gunzip < /root/backups/db-sitemanager-<stamp>.sql.gz | mysql sitemanager`
  (откат ядра обычно не требует откат БД, но если обновление меняло структуру — да).
- **nginx/php-fpm конфиги**: бэкапы в `/root/backup-fix-20261111/`.
- Apache-фолбэк: `systemctl start httpd` (сейчас остановлен и отключён из автозапуска).

## 5. Риски и заметки

1. **Сторонний модуль `mibok.rasp` 2.4.0 от 2018-12-05** (расписание) — не обновляется апдейтером ядра; совместимость с PHP 8.3 обеспечена нашим патчем (статические методы). После любых обновлений проверить `/raspisanie/`.
2. Официальное требование Битрикса «сначала обновить ядро, потом PHP» — у нас PHP уже 8.3, поэтому обновление ядра выполняется **на PHP 8.3**; при ошибках возможен временный откат PHP на 7.4? — нет: конфиги nginx/php-fpm на PHP 8.3, откат PHP потребует возврата конфигов (бэкапы есть). Лучше обновлять на staging до прода.
3. После обновления очистить кэш (админка → Автокеширование) и проверить работу cron-агентов (cron уже на PHP 8.3 CLI).
4. Не включать композит до обновления — он и так заблокирован архитектурой шаблонов (`COMPONENT_VOTING`).
