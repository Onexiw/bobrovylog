## 2. Что сделано

1. **gzip расширен**: добавлены типы `application/json`, `application/xml`, `text/xml`, `text/plain`, `image/svg+xml`, шрифты (`nginx.conf`).
2. **brotli включён** (модуль `ngx_brotli` уже был собран в nginx): `brotli on; comp_level 5; types ...`.
   Проверено: ответы отдаются с `Content-Encoding: br`.
3. **HSTS включён** на обоих площадках:
   `Strict-Transport-Security: max-age=31536000` (без `includeSubDomains` — чтобы не влиять на поддомены до их проверки).

5. Бэкапы конфигов nginx: `/root/backup-fix-20261111/nginx-20261111/`.

## 3.2. Композитный кэш: эксперимент на staging (11.11.2026)

Проведён полный эксперимент по штатному включению композита на staging:

1. Ручное включение (`.enabled` + опция `~PARAM_COMPOSITE=Y`) — **недостаточно**: `Composite\Engine::isEnabled() = N`.
2. Штатное включение через API Битрикса (`\Bitrix\Main\Composite\Helper::setEnabled(true)` через CLI): зарегистрированы обработчики (`OnEpilog`, `OnLocalRedirect`, `OnChangeFile` в `b_module_to_module`), создан `.enabled`, `Engine::isEnabled=Y`, `getUseHTMLCache=Y` — подтверждено пробником в реальном запросе.
3. Включён отладочный лог композита (`b_composite_log`) — выяснена причина отсутствия кэширования:
   **`COMPONENT_VOTING`** — страницы содержат компоненты, которые Битрикс считает «голосующими»/динамическими (шаблоны меню `mx_top_menu`, компонент расписания `mx_mibok`, фильтры). При их наличии страница не кэшируется.

Вывод: композит **не включается одной настройкой** — требуется адаптация шаблонов (выделение динамических областей / фреймов, отказ от «голосующих» компонентов в кэшируемых зонах). Это отдельная задача по кастомизации шаблонов, а не быстрый оптимизационный тумблер.

Состояние: эксперимент полностью откачен (композит выключен, `.enabled`/логи удалены, кэш очищен), staging и прод — 200.

Потенциал: при адаптации шаблонов TTFB анонимных посетителей может упасть со ~0,1–0,2 с до ~0,01–0,03 с (сейчас страницы уже отдаются из managed-кэша Битрикса за ~0,1 с).

Эксперимент: добавили `opcache.jit_buffer_size=64M`, перезагрузили php-fpm (`jit_enabled=Y`), замерили снаружи (8–10 запросов на страницу, median):

**Вывод: прироста нет** — TTFB определяется сетью и накладными расходами фреймворка, а не CPU. JIT откачен (конфиг восстановлен), чтобы не добавлять риск.
